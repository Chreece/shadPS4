Experimental xstate tracing inside shadPS4 (Linux x86-64)

This diagnostic homebrew is for the emulator only. Do not install this variant
on a physical PS4. main.cpp and cases.S remain the unmodified console probe;
build_trace_probe.py creates a marked or unmarked emulator variant in an output directory.

Build the candidate with ENABLE_EXPERIMENTAL_XSTATE_TRACE=ON. The validation
candidate also includes #5329, which makes guest memory protection independent
of GPU write watches. The feature is OFF by default.

With the candidate binary, OpenOrbis SDK, Clang, LLD, make and Xvfb available:

python3 hardware/cpu_xstate/run_trace_emulator.py \
  --emulator /path/to/candidate/build/shadps4 \
  --sdk /path/to/OpenOrbis/PS4Toolchain \
  --output /tmp/shadps4-xstate-trace

For automatic interception without markers, add --unmarked --timeout 900.
The runner sets SHADPS4_XSTATE_TRACE_AUTO=1 for its child emulator only.
Without that variable the experimental build keeps the original marked mode.
Automatic mode starts at the main guest entry, new pthread entries, module
initializers and guest signal callbacks. Tracing pauses during host-only module
loading/static patching and native pthread creation/exit. Native pthread setup
temporarily blocks signals and must not inherit the diagnostic trace flag.

Use --icd /path/to/lvp_icd.json to select a software Vulkan driver if required.
The runner builds the diagnostic, creates a separate emulator profile, runs it
with a null GPU and its own display, checks the results, then archives the logs.
It only stops the emulator and display processes it started. No installed
emulator, games, saves, SSH session or streaming-session guard is changed.

Checks:
- 224 original register and exception cases compared with the PS4 capture.
- Generated instructions rewritten 64 times with W-to-X permission changes and
  64 times while remaining RWX. The guest code bytes must remain unchanged by
  the tracer after execution.
- XGETBV in 35 nested guest exception callbacks.
- Trap number, read/write fault details and the fault address in those callbacks.
- A callback repairs ECX and retries a faulting XGETBV at the original address.

The start marker is INT3 followed by the eight-byte NOP
0f 1f 84 00 58 53 4f 4e; the end marker uses 46 as the last byte.
Without automatic mode, only marked regions are traced. Automatic mode needs
no marker bytes and executes the original cases.S probe instructions unchanged.
Both modes read instructions afresh at execution boundaries, with no rewritten
guest instructions or translated-code cache. Module helper trampoline ranges
are excluded from guest xstate interpretation, so they can save full host state.
Guest PUSHF/PUSHFQ hide the internal trace flag. POPF/POPFQ restore guest flags
while keeping interception active. Signal returns are checked before execution
resumes, including callbacks that change the instruction pointer.

Additional automatic-mode checks:
- 64 flag restore tests covering 16-bit and 64-bit forms, including DF and OF.
- Two simultaneously released guest threads executing 256 generated XGETBVs.
  One returns normally; the other exits through scePthreadExit. Both are joined.
- An illegal-instruction callback redirects RIP directly to unmarked XGETBV.
- Startup's inline XGETBV is unchanged and must report 7.

The unmarked variant optimizes only output formatting and the unchanged-tail
check: SIMD equality checks all bytes from 832 to 81919; the original extent
scan still runs if any byte differs. No CPU test cases or masks are removed.

Limits:
- This is a slow diagnostic path. It single-steps native execution and is not
  suitable for normal gameplay. Performance requires a different execution path.
- Guest code that requests its own single-stepping, uses IRET or changes SS is
  rejected rather than silently escaping interception. Debuggers, transactional
  execution and unusual flag/context manipulation are not validated.
- All tested code rewrites occur between calls. This does not make concurrent,
  unsynchronized writes to executing code safe.
- Main, pthread and signal-callback entries have dedicated runtime checks.
  Module-initializer hooks compile and run during startup but do not have a
  separate xstate-specific fixture. Every possible native-to-guest callback has
  not been audited. There is no cross-platform runtime implementation here.
- Saved-state bitmaps still use native in-use tracking. The host may mark an
  initial SSE component in use even when Jaguar does not. Empty x87 register
  data is not a deterministic comparison target.
- Unsupported native state (such as guest MXCSR bits unavailable on the host)
  stops the diagnostic; there is no software arithmetic fallback here.
- This does not implement generated CPUID/RDPID, a complete Jaguar feature
  model, or Windows/macOS support.

For a shorter flags/thread/redirect diagnostic, use --unmarked --auto-only.
That mode does not run or claim the 224-case hardware comparison.

The normal console FPKG is unchanged and still uses the original unmarked probe.
